# P4P Public Surface

This document explains how the current P4P public lane is split across website,
GitHub, and owner-facing print collateral.

## Four Public Layers

### 1. `pizza4people.com`

This is the owner-facing public proof front door.

It should answer:

- what Pizza4People is
- why the direct route matters
- what exists now
- what is proof versus next-gate pilot work

It is the clearest public place for restaurant-facing first understanding.

### 2. GitHub repo

The public repo is the protocol/proof/method layer.

It should answer:

- what P4P is claiming right now
- what the wire contract is
- what the architecture preserves
- what code and docs back the public claim

It is not the same thing as the owner-facing first-contact surface.

### 3. Owner-pack print collateral

The owner pack is the offline first-contact and follow-up support layer.

It exists for:

- handoff in person
- leaving material with a shop
- explaining the first pilot without dropping straight into GitHub or site
  navigation

The print pack is part of the public explanation layer, but it is not
automatically public-downloadable from the site until it is marked ready.

### 4. `protocols4people.com`

This is the broader umbrella direction.

It should not be treated as the first restaurant-facing entrypoint.

For a local shop owner, `Pizza4People` is the clearer front door.

## Naming Rules Across The Layers

Owner-facing print collateral:

- `Pizza4People` first
- `P4P` secondary

GitHub and technical docs:

- `P4P` / `Pizza4People` together where helpful
- protocol and proof language may be more explicit

Broader umbrella framing:

- `Protocols4People` stays the wider family direction
- not the default opening frame for the first restaurant conversation

## Practical Reading Order

If the reader is a shop owner:

1. owner pack
2. `pizza4people.com`
3. GitHub only if they want the deeper proof layer

If the reader is technical:

1. `README.md`
2. `PROOF.md`
3. `docs/`
4. `pizza4people.com` as the human-facing public layer

## Rule

Do not let one surface silently replace the others.

The website, GitHub repo, and owner-pack each have different jobs.

The public lane gets confusing when:

- GitHub tries to be the owner handout
- the website tries to hold every protocol detail
- print material tries to become both zine, guide, and technical spec at once

Keep the surfaces distinct and linked honestly.
