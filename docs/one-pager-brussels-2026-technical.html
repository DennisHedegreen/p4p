DISCOVERY WITHOUT
PLATFORM RELAY.

Use this when the group needs the deeper technical version: discovery can use a registry, but menu and order traffic still go directly from client to node. The registry must not become the order path.

announce -> heartbeat -> discover -> menu -> order client -> registry for discovery client -> node for menu and order backup registry only for failover

Technical Claim The Group Can Stand Behind

P4P proves that a local takeaway shop can stay directly reachable without a marketplace middleman owning first contact, while keeping discovery and ordering as separate layers.

Core Wire Loop

  1. node announces itself to one or more registries
  2. node heartbeats keep stale entries out of discovery
  3. client queries registry for nearby nodes
  4. client fetches menu from the node endpoint
  5. client submits order to the node endpoint
  6. client can fail over to a backup registry
discover: client -> registry menu: client -> node order: client -> node mode: order_mode = test | live backup: client -> backup registry

Why It Is Technically Interesting

  • registry out of order path
  • node-owned endpoint and menu truth
  • explicit order consent via order_mode
  • failover at discovery layer
  • modules outside minimum interoperable core

Anti-Capture Boundary

This is not just another ordering backend. The point is to keep the minimum interoperable core small enough that a shop can remain directly reachable and a registry can help discovery without owning the customer relationship.

Technical Version The Group Can Show

  • one small registry
  • one small shop node
  • one browser client
  • one operator screen
  • request trace that proves menu/order hit node, not registry
  • optional backup registry if time allows

Hard Non-Goals

  • production security story
  • online payment rail
  • delivery logistics
  • restaurant rollout
  • mature federation
  • trust/certification ecosystem
